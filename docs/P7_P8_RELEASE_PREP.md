This command has only been tested against synthetic results; it has **not** yet captured the hosted project or passed the production-derived gate.
  - **The capture role's privileges matter and a plain `SELECT`-only "read-only" role is not enough.** Verified empirically on PostgreSQL 17 with a synthetic restricted role (2026-10-04): `scripts/p4-equivalence-production.sql` needs a connection role that can (1) `USAGE` on schemas `public` and `auth` and `SELECT` on every `public` table and `auth.users`; (2) **execute the reader functions and `set local role authenticated`** — both come from **membership in `authenticated`** (`GRANT authenticated TO <role>`, which on PostgreSQL 16+ carries `INHERIT` and `SET` by default); and (3) **bypass RLS** — a role with the `BYPASSRLS` attribute, or an owner/superuser connection such as Supabase's `postgres`. All three are required. With `SELECT` + `authenticated` but **no** RLS bypass, the batch still succeeds but silently under-captures: the id lists it enumerates with no JWT set (`gate.ints/gate.mems/gate.users`, SQL lines 79–82) and the exported rows are RLS-filtered, so per-account reader facts and table rows go missing. The gate then fails at step 4 ("the copy does not reproduce production") because its copy-side capture runs as the local superuser and enumerates everything — a confusing failure that does not name the missing privilege. Creating this role on the hosted project is a production change for the owner; deliver its URL only through `DVD_READONLY_DATABASE_URL` in the environment, never in chat.
